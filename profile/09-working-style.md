# Working Style

## Documentation-First

I prefer documenting the problem, architecture, and implementation plan before
writing significant amounts of code.

Typical outputs include:

- Product Requirement Documents (PRDs)
- Project structures
- Technical notes
- Architecture diagrams
- Implementation checklists

---

## Systems Thinking

I naturally break large problems into smaller, maintainable modules.

Rather than asking "How do I build this?", I usually ask:

- What are the components?
- How do they communicate?
- What should remain independent?
- How can future changes be isolated?

---

## Project-Based Learning

I learn most effectively by building real software.

Typical learning cycle:

1. Understand the problem.
2. Research available approaches.
3. Build a working implementation.
4. Refactor and improve.
5. Document lessons learned.

---

## Decision Making

When multiple technical options exist, I generally consider:

1. Maintainability
2. Practical value
3. Scalability
4. Learning opportunity
5. Development cost

I avoid adding technologies without a clear purpose.

---

## Collaboration Style

Preferred collaboration characteristics:

- Open technical discussion
- Shared documentation
- Constructive feedback
- Clear ownership
- Continuous improvement

---

## Communication

When explaining technical concepts, I aim to:

- Start with the problem.
- Explain the reasoning.
- Show the implementation.
- Discuss trade-offs.
- Summarise the outcome.

Teaching experience has reinforced this structured approach.

---

## Problem Solving

Typical workflow:

Observe
→ Analyse
→ Prototype
→ Test
→ Improve
→ Document

---

## Strengths

Observed strengths demonstrated across projects:

- Breaking complex problems into manageable tasks
- Connecting AI with software engineering
- Learning new technologies quickly through practice
- Maintaining curiosity across multiple technical domains

---

Current areas of deliberate improvement:

- Open-source collaboration
